# Frame flash limiter passes

Portable GLSL for the frame flash limiter: six fragment passes that hold back any part of the
frame whose luminance or red transitions would exceed the flash-area limit. They reproduce the
reference model `tools/shader/limiter-model.mjs` (model `pixel-10deg`) bit for bit. The
conformance vectors in `conformance/limiter/frame/` are the spec. `make limiter-check` checks the
model, the generated GLSL ES 3.00 and Metal, and the WebGL2 and Metal passes against those vectors.

`tools/shader/limiter.mjs` wraps each pass the way `present.mjs` wraps the present pass:

- GLSL ES 3.00 for WebGL2;
- GLSL 450 through glslangValidator and SPIRV-Cross (pinned) to Metal, with the ABI checked.

Each pass is `luma-lut.glsl` (rows and output only, behind `#define LIMITER_LUT`), then `common.glsl`, then `<pass>.glsl`.
`luma-lut.glsl` is generated by `node tools/shader/limiter.mjs --write`; do not hand-edit it.

## Bindings

| Resource | WebGL2 | Metal |
|---|---|---|
| `LimiterBlock` (32 bytes, std140) | uniform block, binding 0 | `[[buffer(0)]]` |
| Textures, in the order listed per pass | units 0.. | `[[texture(0..)]]` |
| Sampler | none: every read is `texelFetch` | `[[sampler(0)]]`, any state |
| Outputs | `location` 0.. | `[[color(0..)]]` |

The uniform block holds two vectors:

- `limiter0 = (cols, rows, limit, refill)`
  - `cols` and `rows` are the window size in cells: the fewest whole cells that contain the 10°
    field wherever it sits.
  - `limit` is the area limit in pixels, a quarter of the field's pixels; a window is over when
    its count is strictly greater.
  - `refill` is the token refill this frame: `earned = carry + clamp(2 * maxFlashHz * dt, 0, 1) *
    65024`, `refill = min(65025, floor(earned))`, then `carry = min(1, earned - refill)`, starting
    at 0. Carrying the fraction keeps a small `maxFlashHz` at a high frame rate refilling; without
    it every frame floors to 0 and a spent budget never returns (Codex round 15). The rate is one
    unit under a token a token period, so the carry, under one unit, cannot finish a token early
    (Codex round 16).
  - On the first frame after the host writes `G` (a start, the fade of a change to the frame, a
    viewing-geometry change), `refill` is 0 and `carry` restarts at 0: time that passed before
    `G` was written does not repay it. `deltaMs` stays the real interval, which ages the
    trackers' stamps (Codex round 16).
- `limiter1 = (tick, deltaMs, 0, 0)`
  - `tick` is `floor(ms / (1000/15/64)) mod 240`; the recency stamps use `tick >> 4`.
  - `deltaMs` is the frame interval as float32: a lower bound on the time the previous frame was
    shown, never more. A host that cannot see paint times takes the shorter of its frame clock's and
    its wall clock's intervals since the last draw. The previous frame may have been painted one
    refresh late and this one on time, so it was shown for max(R, interval - R) for the display's
    refresh period R. A host that knows R only from above takes the least of that over every R up
    to its bound, max(interval / 2, interval - bound), and no more than the bound (the Beamfall web
    host: the bound is the shortest draw interval seen, at least 4 ms and at most a 24 Hz refresh;
    animation frames can run at every other refresh, so a host drawing at its animation-frame rate
    credits half of each interval) (Codex rounds 18 to 21). R is the period at both paints: a
    display that changes its refresh rate between them can show the frame for less, which a host
    without paint times cannot see, so such a host over-credits one interval, by at most its
    bound, on a refresh-rate change (Codex round 22, OSC-0046). A host that credits less than the
    time shown ages evidence slower and holds changes longer.
  - The limiter steps its trackers on every frame it outputs, so a host SHALL present every frame
    it draws, each at most one refresh late. A frame drawn but never presented leaves the trackers
    a step the screen never showed, and a transition the screen does show can then go uncounted.
    Browsers do not report a dropped canvas paint; the web host draws once per animation frame,
    which a browser presents or delays rather than replaces. Presentation feedback, where a
    platform gives it, is tracked in OSC-0046.

`windowOf(geometry, width, height)` in `tools/shader/limiter-geometry.mjs` gives `cols`, `rows`
and `limit` for a device class and frame size. `createClock` in the model gives `tick`, `deltaMs`
and `refill`.

## Frame size

Frames from 64 x 36 to 8192 x 8192 pixels. The area limit is a quarter of the field's pixels,
passed as a float, so it is exact only while it stays under 2^24; at 8192 x 8192 it is at most
2^24. Hosts clamp the frame to 8192 on each side. (Until v0.2.9 the `reduce` pass packed
per-direction counts in 16 bits; the counts are 32-bit now.)

## Texture formats

| Type | WebGL2 | Metal |
|---|---|---|
| frame, history, output | RGBA8 | `rgba8Unorm` |
| row, sub-block and cell counts | RGBA32UI | `rgba32Uint` |
| tracker state, window flags, grant | RGBA16UI | `rgba16Uint` |

## Passes

Run the passes in order each frame. Each pass draws one full-screen triangle into a framebuffer
of the size shown. The entry point is `oscillux_limiter_<pass>`.

| # | Pass | Size | Textures | Outputs |
|---|---|---|---|---|
| 1 | `rows` | 64 x frame height | `uFrame`, `uTrack` (previous) | `oR` = (count, directions firing now \| recent directions << 4, 0, 0): per sub-block column and pixel row, the pixels whose tracker fires now or fired within the coverage interval, in any channel and direction |
| 2 | `reduce` | 64 x 36 | `uRows` | `oS`, the same layout summed over the sub-block; a sub-block requests each direction one of its pixels fires in now |
| 3 | `cells` | 16 x 9 | `uS` | `oC` = (count, requests, 0, 0): the cell's pixel count, directions firing now and recent directions << 4 |
| 4 | `windows` | 16 x 9 | `uC` | `oW` = (over, 0, 0, 0): 1 when the window with its origin at this cell counts more than the limit |
| 5 | `grant` | 1 x 1 | `uC`, `uW`, `uG` (previous) | `oG` = (admitted bits \| held bits << 4 \| second luma token << 8 \| last red grant was down << 9 \| red refill remainder << 10, luma token deficit, red token deficit, luma credit) |
| 6 | `output` | frame | `uFrame`, `uHist` (previous output), `uTrack` (previous), `uG` (this frame) | `oColor`, `oTrack` |

Directions are bit 0 luma rising, bit 1 luma falling, bit 2 red rising, bit 3 red falling.
The held bits are the directions some pixel fires in that the grant did not admit: while they are
clear the output shows the input exactly, so a host may stop drawing a paused frame (Codex round
18). Until v0.2.9 bits 4 to 7 were the over flag, set in every direction together.

The `grant` pass keeps two token deficits: luma in `oG.y`, red in `oG.z`. Luma over the limit
takes the luma token when its deficit is zero. Red over the limit takes the red token when its
deficit is zero; the red token refills at an eighth of the luma rate, so no 1 s window holds two
large-area red transitions (no red flash) and a held red change is admitted instead of freezing
(CORE-2382): the red token is back by the first frame at which the `deltaMs` of the frames after
the spend, each counted up to one refill period of 1 / (2 maxFlashHz) s, add up to
(65025 / 65024) · 8 periods, and the change is admitted on that frame unless it asks luma too and
the luma token is not ready (below).
At a steady cadence that is 1.333 s and a frame at the default 3 Hz, or the ninth frame after the
spend when every frame is longer than a period; a mixed cadence of long and short frames takes
longer than either, because a long frame earns only one period (Codex round 20). A host write
of `G` is not a grant: it writes the red token spent and the first frame after it earns nothing,
so after `setGeometry` a red change held from its first frame at 250 ms frames is admitted on the
tenth (Codex round 21). A refill period earns 65024 / 8 red units and a frame's refill is capped
at one period, so eight periods repay 65024 of the red token's 65025 and the last unit takes
8/65024 of a period more (Codex rounds 17, 19 and 21). The bound is the red token's, not the
admission's. A frame that asks luma too is admitted only when the luma token is ready as well, so
a luma grant shortly before the red token returns holds the change until the luma refill after
that grant, counted the same way: at most (65025 / 65024) · 3 periods, one for a single grant, two
for a pair, and one of credit when the frame asks both luma directions. At 60 frames a second and
the default 3 Hz, a white rise two frames before the red token returns holds a full-frame red
change nine frames past it. A frame grants nothing until every token it asks is ready, so no
luma is granted while the change is held and it waits for one luma refill, not a train of them
(Codex round 25). The red
bound is per grant: red grants one direction
at a time, so an area held both rising and falling is admitted in two steps, the second one bound
after the first (Codex round 18). When both red directions are asked, one is
admitted, the other than last time. A frame asking both channels is admitted only when both
tokens are ready: a pixel changing in both shows the change only when both are admitted, so a
grant of one alone would spend its token on a held change (Codex round 13). When something
fires now, a channel firing nowhere but changed recently in the frame is asked too, in one
direction (rising when it rose), so its own token pays for the combined area: red changing alone
under the limit and luma over it a frame later cannot spend only the luma token (Codex round 14).
The red refill is exactly an eighth of the luma refill: the remainder of each division by 8
carries to the next frame in bits 10 to 12 of `oG.x`, so a tiny `maxFlashHz` or a tiny frame
interval neither freezes red nor returns its token early. (The first v0.2.9 drafts rounded each
red refill up to one unit, which at a 10 µs interval returned the token in 650 ms; Codex round 16.)

Pixels flash together whichever way and in whichever channel they change, so the area is one
count of pixels changing in any channel and direction; over the limit, every direction is over
(WCAG's combined area; until v0.2.9 opposite-phase patches and adjacent luma and red patches
passed, Codex rounds 12 and 13).

## Flash measure

Luma and red are measured in integer codes, and the codes are the measure: the limiter and the
pixel auditor both use them, so neither can disagree with the other. A luma code is the sum of
`round(65535 · Y)` per channel halved to 15 bits, 0.74 above to 1.24 below `32767.5 · Y` over
every 8-bit colour; the luma step is 3275 codes (0.1, 3276.75 less both errors) and the darker
side below 26215 (0.8, 26214 plus the upper error). A red code is `(R - G - B) >> 8` of the linear
channel codes wherever `R > G + B`, 0.006 above to 1.002 below WCAG's quantity in 256ths; the red
step is 15 codes (20 on WCAG's 320 scale, 16 less both errors). So every WCAG transition fires.
Every change moves the red tracker; it counts as a red transition when a saturated red state
(`R / (R + G + B) >= 0.8`, widened by the codes' rounding) is the new state or was seen since the
previous change, or, when it did not count, at the first saturated state before the next change.
Every WCAG transition between saturated red and any other state counts. A change between two
unsaturated reds or oranges counts only when a saturated state was seen since the previous change,
so a pixel that left saturated red through an uncounted step still pays for the step after it
(Codex round 20); a strobe between two oranges never counts. (Until v0.2.9 the thresholds were widened by the codes'
rounding and red required saturation on both states, Codex rounds 11 to 13; until round 13 an
unsaturated reversal left the red tracker unmoved, which hid the transition after it.)

## Per-pixel trackers

Every pixel carries the pixel auditor's trackers in one RGBA16UI texel (`common.glsl`):

- `x`: the luma tracker's extreme (15-bit); bit 15 is the high bit of the red memory.
- `y`: the luma tracker's distance (12-bit); bit 12 set when it last fired rising, bit 13 when the
  pixel has no state yet (the reference model's start); bit 15 is the low bit of the red memory.
- The red memory (x bit 15, y bit 15): 00 unknown, 01 the red tracker's latest change counted and
  no saturated state seen since, 11 that change has not counted, 10 it counted and a saturated
  state was seen. The zero texel (a reset, or a host's first frame) is unknown: the next red step
  counts at once and, unless its new state is saturated, counts again at the first saturated state;
  a saturated state with no step counts the tracker's direction. So a reset never hides a red
  change, whatever the pixel showed before it (Codex rounds 18 and 19).
- `z`: the red tracker's extreme | distance << 8 (4-bit) | rising << 12.
- `w`: four 4-bit recency stamps (luma up, luma down << 4, red up << 8, red down << 12); 0 is
  none, else the event's unit `(tick >> 4) + 1`.

Each tracker has a direction (the way it last fired), an extreme since then (the peak after a
rise, the trough after a fall) and a reference, stored as its distance from the extreme, which
stays under a step. The reference is the level at the last transition, moved back with any change
short of a step against the direction (the lowest dip since a rise, the highest since a fall), so
a dip short of a step and a step up from it is a rise (Codex round 17). A tracker fires when the pixel moves a full
step (luma 0.1, red 20 on WCAG's scale) with the darker side below 0.8: back from the extreme (a
reversal), or onward from the reference (a further step the same way). A change over many frames
counts as soon as it adds up to a step, and the area counts pixels exactly whatever share of a
sub-block moves. An onward rise whose darker side is not below 0.8 moves the reference without
firing; an onward fall that ends above 0.8 keeps its high side (a code under a step from the
trough), so it fires when the trough goes on below 0.8 (Codex round 18). Counting each step of a threshold, not one per direction, matters for areas: pixels that
started rising at different times can reach a step together, and a large area whose pixels fired
one at a time under the limit then makes its joint rise and fall uncounted (Codex round 16; until
then steps in one direction were one transition). The pixel auditor counts the same way.
`output` shows history at a pixel whose trackers would fire on the input in a direction the grant
did not admit and the input everywhere else (until v0.2.9 the whole sub-block held, so holds
showed as tiles), then steps every pixel's trackers on the colour it shows. The trackers
therefore hold the auditor's state of the output, and the output makes only the transitions the
grant admitted. (Until v0.2.9 the limiter tracked 64 x 36 sub-block means: a change over a fifth
of a sub-block, or a slow cycle under a step a frame, escaped it; Codex round 7, CORE-2543.)

## Ping-pong and reset

Keep two copies each of `G`, the tracker state and the output. A frame reads copy `a` and writes
copy `b`, then the host swaps them. `output` reads this frame's `G` (copy `b`).

`rows`, `reduce`, `cells` and `windows` write single textures that are rebuilt every frame.

At start the host writes `G` fully spent, as on every later write, so the first frame is rationed
like any other and refills 0 (Codex rounds 17, 18, 24): a host cannot rule out that its view showed
content before its first frame (a remount, a reused surface). `G` cleared to zero, both budgets
full, is safe only where the view showed black until the first frame; the reference model and the
conformance vectors start from it, and it counts as a write too. The host also starts the output
black and the tracker state at zero: tracked black, the value the view showed before the first
frame. Content then rises from black
through the grant like any other change. After a lost context is restored the view showed content
before the loss, so the host starts as after the fade of a change to the frame (below): black
presented without the limiter for longer than the coverage interval, then everything tracked
black and `G` written fully spent. The zero texel is a tracker falling at 0 with every luma
change counted and the red memory unknown. (A texel with bit
13 of `y` set means no state yet: a pixel with no state takes its first value without firing, as
if it fell to it. The reference model and the conformance vectors start from it; a host does not,
because it would pass its first frame, or the first frame after a reset, with no budget charged,
CORE-2516.)

`G` and the tracker state of a frame on screen are never cleared. When only the window changes
(the viewing geometry: the same frame at the same display scale, all of it still in view), the
host passes the new window and limit, keeps the trackers and writes `G` fully spent (x = 256,
y = 65025, z = 65025, w = 0): two luma tokens and the red token of deficit, so no luma transition
is granted for 2 / (2 · maxFlashHz) seconds and no red transition for 8 / (2 · maxFlashHz)
seconds. A smaller window can put pixels that fired recently, each admitted while under the old
limit, over the new one with no grant paying for them. (Until v0.2.9 `G` was kept, Codex round
12.)

### A change to the frame: fade, black, start

The display scale is the number of physical pixels a frame texel covers. What the viewer sees is
fixed by the frame's size in texels, its display scale and the texels of it in view. When any of
them changes (the view is resized, the device pixel ratio or page zoom changes, the host takes
another texel size, the view clips more or less of the frame), the host takes one path, the same
for every change. Nothing is carried from the old frame to the new one.

1. **Fade.** Keep the frame on screen as it is: its size, its scale, its place and its trackers.
   Write `G` fully spent, pass an area limit of 0 and feed the limiter black in place of the
   visual. Under a limit of 0 one pixel that fires puts its windows over, so every fall to black
   waits for a grant however little of the frame is still in view, and the grant paces the fall
   like any other transition. The fall is asked from the fade's first frame and in one direction
   a channel, so the grant has admitted it once the red token is back: the luma tokens it also
   waits for return sooner. The fade is over when a frame of it has shown black at every pixel.
   A host that reads the grant word knows when: a frame of the fade whose held bits (4 to 7 of
   `oG.x`) are clear showed its input, black, exactly, and the fade ends at the next frame. The
   first frame of the fade reads the `G` the host wrote, which says nothing; the word that counts
   is the one a frame of the fade wrote. A frame with no pixel a step above black is black on the
   fade's first frame, one with luma to drop when the two luma tokens are back
   (2 / (2 · maxFlashHz) seconds), and one with saturated red when the red token is. A host that
   does not read the word, and any host as a cap, runs the fade for longer than the red token's
   refill, 8 / (2 · maxFlashHz) seconds, by more than two frames (the first after the write
   refills nothing, and the grant comes on a frame). Both times are in the time the limiter is
   credited with, not on the clock (the Beamfall web host: the held bits of the frame before,
   with a cap of 2 s, counting each frame's `deltaMs` up to one luma token's refill, the most a
   frame refills, so a slow page fades for longer; Codex rounds 22 and 26). The output is then
   black.

   Credited time runs slower than the clock wherever `deltaMs` is a lower bound. The Beamfall
   web host cannot read the display's refresh period, so at a steady cadence it credits half of
   each interval (`limiter1` above): its credited times take about twice as long on the clock.
   At 60 frames a second and the default 3 Hz a frame with luma to drop is held about 0.7 s and
   a saturated red one about 2.7 s before it falls, and the cap of 2 s is about 4 s.
2. **Black.** Free the frame and present black, without running the limiter, for longer than the
   coverage interval counted from the first black frame presented (the Beamfall web host:
   0.1 s of credited time, about 0.2 s on the clock at 60 frames a second). Every tracker stamp from before has then left the coverage interval. A view with no
   whole texel to show stays black.
3. **Start.** Start a frame at the size, scale and view asked for then, as at the first start:
   output black, trackers zero, `G` written fully spent. Content returns from black through the
   grant as the budget refills.

A further change during the fade or the black only changes what step 3 starts at. It does not
reallocate, write `G` again or restart either clock, so a view dragged to a new size costs one
fade and one start, not a reset a frame.

Through the fade the view of the old frame may only shrink. A pixel that leaves the view leaves
by the host page's clip: the limiter cannot hold what is no longer drawn, and the limit of 0
covers whatever is left. A pixel the view hid must not come back before the start: it would show
the frame's colour with no tracker event. So the host keeps the frame at its size and place and
clips it to the smallest view since the frame started (the Beamfall web host clips its canvas
over a black backdrop, Codex rounds 24 and 25). Cutting the frame itself to the smaller view
would drop the lit pixels of a texel still partly on screen to black with no grant.

The host sizes the view to exactly the frame times the display scale in physical pixels and
letterboxes the rest, so every texel covers the same whole number of physical pixels, and it
passes the area limit of the physical field divided by the texel area. A frame shows whole
texels only. A texel the view cuts when the frame starts is not presented: its pixels stay black,
the level every tracker starts at, and the area limit comes from the texels in view. A view that
comes to show that texel whole, or to cut a texel it showed, is a change like any other (the
Beamfall web host takes one-pixel texels for a view narrower than its texel, so it has a whole
texel to show, Codex round 22). Wherever the view shows no judged pixel (past the frame, through
the clip, during the black) the host shows black.

Only black crosses a change. Until v0.2.9 the host held the old size stretched to the view, which
moved patterns on screen, and the first v0.2.9 drafts cleared to black at once, which could
itself complete a flash with the transition before it (Codex rounds 12 and 13). Later drafts kept
pixels alive across a change: a 1:1 copy of the overlap at one display scale, a k x k copy on a
drop to a divisor of the scale, a held view over a cut texel. Each needed its own proof and each
left a seam for the next (Codex rounds 16 to 25), so they are gone. The change itself is the
user's (a zoom or a move to another display); the browser rescales the last frame before any
host can react, which the limiter does not control.

None of the passes allocate. A host creates the textures once per frame size. The tracker state
costs 8 bytes a pixel per copy: 133 MB at 4K for the two copies (66 MB each).

## Cost

Measured with `node tools/shader/limiter-check.mjs --metal --time 1920x1080`. On an M2 Max the
passes cost 0.31 ms of GPU time per frame at 1080p and 0.87 ms at 4K. The `rows` and `output`
passes scale with resolution; the rest are fixed size.
